# hrva.cc — URL Shortener Frontend

Next.js 16 App Router + React 19, deployed on Cloudflare Workers via `@opennextjs/cloudflare`. Deployed at [hrva.cc](https://hrva.cc).

## Commands

| Command | Purpose |
|---------|---------|
| `npm run dev` | Next.js dev server (TurboPack) |
| `npm run build` | Standard Next.js build |
| `npm run build:cf` | Cloudflare Worker build |
| `npm run preview` | Build + Cloudflare local preview |
| `npm run deploy` | Build + Cloudflare deploy |
| `npm run cf-typegen` | Regenerate `cloudflare-env.d.ts` from wrangler config |
| `npm run lint` | ESLint (`eslint .`) |
| `npm run check:utm` | Node assertions for `lib/utm.ts` (`scripts/check-utm.mjs`), prints `ok` |
| `npm run check:share` | Runs `check:invisible`, then Node assertions for `lib/share.ts` (`scripts/check-share.mjs`), prints `ok` |
| `npm run check:notifications` | Runs `check:invisible`, then Node assertions for `lib/notifications.ts` (`scripts/check-notifications.mjs`), prints `ok` |
| `npm run check:domains` | Runs `check:invisible`, then Node assertions for `lib/domains.ts` (`scripts/check-domains.mjs`), prints `ok` |

`npm run dev` proxies `/api/v1`, `/oauth2`, `/login` and `/api/changelog` to `http://localhost:8080`, and dev short links (`getShortBaseUrl()`) use the same origin. Set `DEV_API_ORIGIN` when starting the dev server to target another backend, e.g. `DEV_API_ORIGIN=http://localhost:18080 npm run dev`; it's read once at startup (`next.config.mjs`), so restart to change it.

No test framework is set up.

`npm run lint` exits 1 on this branch: the baseline is **8 errors and 2 warnings**. A change passes lint when the totals don't rise and no file it touches has a problem. Count them with `npx eslint . -f json | jq '{errors: ([.[].errorCount] | add), warnings: ([.[].warningCount] | add)}'`.

## Architecture

### Routing (`app/`)
- `/` - Landing page (public URL shorten + logged-in experience). `app/page.tsx` is a thin server page: it exports the home metadata (`HOME_TITLE`, `HOME_DESCRIPTION`, canonical `/`) and the `/`-only JSON-LD (WebApplication and FAQPage), and renders the client `HomePage` (`components/home/home-page.tsx`). The H1 is `SLOGAN` ("Short links that count clicks, not people.") and the subline under it is the category line ("A free, open-source URL shortener with no ads."). The `<title>` is `HOME_TITLE`: `HOME_TITLE_TEXT` ("Free URL shortener that counts clicks, not people"), a middle dot and the site name. The FAQ text lives in `lib/home-faq.ts` (`HOME_FAQS`, parts with `{ strong }` for bold), so the visible answers and the FAQPage JSON-LD are the same text; there is no microdata
- `/register`, `/reset-password/[token]` — Auth flows. `/register` has the same **Google** and **GitHub** buttons as `/login`; they clear `post-login-next`
- `/login` — Email and password, **Sign in with a passkey** (`components/auth/passkey-sign-in-button.tsx`, with a **How passkeys work** link under it) and passkey autofill from the Email field (`usePasskeyAutofill`: only while the tab is visible, it runs again when the tab comes back, and never again after a sign-in succeeds). A two-step account gets the shared `SecondStep` screen (`components/auth/second-step.tsx`) with the methods from the login response: **Use a passkey or security key** for `WEBAUTHN`, then **or enter a code** and the code field for `TOTP` / `RECOVERY_CODE` (trimmed before sending; the backend ignores case, spaces and a missing dash). Under it, **Use a different account** returns to the password form with the email kept (password cleared) and **Lost your passkey or codes?** opens `/help/passkeys#lost-device` in a new tab. A 410 returns to the form with the backend's text as the toast (expired, or out of tries), except an expired passkey request from the verify call (`This request expired. Try again.`): that stays on the step, shown under the passkey button, and the next press fetches fresh options. 401, 403 and 400 texts (tries left, account and network locks) are shown as the backend sends them; the browser-side wrong-key text is only for `NotAllowedError`. `?next=` (checked by `safeNext`) is where a sign-in lands; the **Google** and **GitHub** buttons (side by side under "Or continue with", outline buttons linking to `/oauth2/authorization/google` and `/github`) keep it in `sessionStorage` (`post-login-next`) for the callback
- `/auth/callback` — Where Google and GitHub sign-ins come back: `?token=` signs in; `?pendingToken=…&methods=TOTP,WEBAUTHN,RECOVERY_CODE` shows `SecondStep` and removes both from the address bar (`replaceState` in a layout effect; an empty `methods` means none). Its way out is **Back to sign in** (`/login`): a button when there's no code field, a link under the form otherwise. A 410 shows the backend's text on the error card; `?error=` (`no_email`, `account_inactive`, `two_step_unavailable`, `invalid_email`, `github_email_unverified`, `google_email_unverified`, `registration_disabled`, `provider_error`) shows its message, any other code "Authentication failed." GitHub sign-ins use the account's verified primary email; `github_email_unverified` ("Your GitHub account has no verified email address. Verify one on GitHub, or sign in another way.") and `google_email_unverified` ("Your Google account's email address isn't verified.") are the backend refusing an unverified address, and `registration_disabled` shows email sign-up's own text, "Registrations are currently disabled", when new sign-ups are paused and the Google or GitHub account has no hrva.cc account yet. `provider_error` ("Signing in didn't work. Try again, or sign in another way.") is any other failure of the Google or GitHub flow, such as a cancelled consent
- `/about` - "About hrva.cc": who runs it (one person, a HrvaLabs hobby project since 2022), why it counts visits the way it does, how it is paid for (no paid plans, no ads, no data sales), where it runs, the code, status and changelog, and contact. A static server page on `StaticPage` (`components/static-page.tsx`), with `AboutPage` JSON-LD whose `mainEntity` is the HrvaLabs Organization. Linked from the footer (Help & legal) and from `/privacy-first-url-shortener` and the Bitly page. Blog bylines (`PostAuthor`) link the author's name to karlo.cc with `rel="author"`. Its **Support hrva.cc** section (`#support`, before Contact; owner-approved) is one line, "If it's useful to you, you can support it." (not repeating "free, no ads", which How it is paid for already says), and two outline `Button`s, **Revolut** (`https://hrva.cc/revolut`) and **PayPal** (`https://hrva.cc/paypal`), the owner's own short links, opening in a new tab with `rel="noopener noreferrer"` like the footer's external links. The buttons sit outside `prose-custom`, whose unlayered `a` rule would otherwise colour and underline them. The footer's Help & legal column links it as **Support** (`/about#support`), and the privacy policy's "Who else receives data" says donations go through Revolut or PayPal on their own sites. No pop-ups, banners or prompts anywhere else
- `/privacy-first-url-shortener` - "URL shortener without tracking": a static explainer (`TechArticle` + breadcrumbs, no FAQPage) that opens with a self-contained answer of about 150 words, then what any shortener can see, what hrva.cc keeps as daily totals, what it keeps for an hour or a few hours (the visitor hashes and the daily key, rate-limit counters with hashed IPs), what it never stores, "Check it yourself" (the GitHub lines in `lib/source-links.ts`, shared with the homepage code sample), link safety, a not-legal-advice note and four visible questions. Every fact comes from the privacy policy or the backend; change the page with them. Linked from the homepage "Private by default" section, `/about` and the footer (**How visits are counted**)
- `/developers` - "Free URL shortener API": a static page (`TechArticle` + breadcrumbs) with the quickstart (key from `/dashboard/api-keys`, `POST https://hrva.cc/api/v1/urls` with `X-Api-Key`; curl, JavaScript and Python in `CodeBlock`s), the request fields and response (the backend's `CreateUrlDto` and `UrlResponse`; create answers `200 OK`), errors (400, 404 unknown key, 409 alias taken, 429 with its exact text), limits, the two keyless endpoints (`/peek` and `/qr`), Swagger, MCP, status and source. It deliberately gives no rate-limit numbers or API key defaults (owner to confirm before they are published). Linked from the header (**Developers**), the footer (**API quickstart**), the homepage Developers section and `/mcp`
- `/mcp` - the MCP server page: what MCP is, server URLs, set-up per client, the tool table, **Things to ask it** (one example prompt per tool), **What your assistant can see** (only what the tools return; never who clicked), what it can't do and disconnecting. Its title stays "MCP server" because Google already indexes the page
- `/qr` - "Free QR code generator, no signup": a static shell (`WebApplication` `/qr#app` + breadcrumbs, prose on static codes, counting scans, print tips and three visible questions) around the client `QrGenerator` (`components/qr-generator.tsx`): an Address field (`withScheme`, the 2,048-character limit), then `QrCustomizer` with `marker={false}`, so the code holds the address as typed, or a placeholder until something is typed. **Use a short link** creates a short link through `useCreateUrl` (anonymous when signed out) and switches the code to it with the marker back on; signed out, it says links made without an account have no stats page. After a successful shorten, focus moves once to the "The code now opens your short link:" line (`tabIndex={-1}`); a 429 replaces the button with the backend's text in `role="alert"` (`tabIndex={-1}`, focused), with no retry. Like `/utm`, both moves happen inside the click handler after `flushSync`, so editing the address away and back never moves focus. Nothing is sent to hrva.cc unless that button is used. Linked from the homepage free-tools row and QR card, the footer (**QR code generator**) and `/help/stats#qr-scans`
- `/utm` - "UTM builder": a static shell (`WebApplication` `/utm#app` + breadcrumbs, prose on shortening, what each field does and what hrva.cc does with the tags) around the client `UtmBuilder` (`components/utm-builder.tsx`): a Long URL field, `UtmFields` with `variant="tool"` (styled like `home`, with its own intro: hrva.cc only sees the tags if you shorten the link) and real `open` state (open by default), then **Your tagged link** with Copy once there is a destination and a value, and **Shorten it** (`useCreateUrl`, anonymous when signed out). It never calls `rememberUtm`, so nothing is stored, and nothing is sent to hrva.cc unless Shorten it is used. After a successful shorten, focus moves once to the **Short link** line (`tabIndex={-1}`); a 429 replaces **Shorten it** with the backend's text in `role="alert"` (`tabIndex={-1}`, focused), so there is no retry. Both focus moves happen inside `shorten`, right after a `flushSync` state update, never from an effect keyed on derived state: the result line also appears when the visitor collapses and reopens the section or retypes a value, and that must not move focus. The length error is tied to the field with `aria-describedby`. Linked from the homepage free-tools row and Campaign tracking card, the footer (**UTM builder**) and `/help/utm` (both ways)
- `/link-in-bio` - "Free link in bio page with no ads": the static page that explains bio pages to someone without an account (`WebPage` about `/#app` + breadcrumbs): what you get, every button is a checked short link, private view counts, indexing off by default, and the small print (the **Made with hrva.cc** footer and **Report this page**). **Create your page** goes to `/dashboard/bio` (sign-in first when signed out) and **How bio pages work** to `/help/link-in-bio`. Every fact comes from `/help/link-in-bio` and the privacy policy; it shows no example page until the owner opts one in. Linked from the header and footer (**Bio pages**), the homepage free-tools row and Bio pages card, and the **Made with hrva.cc** link at the bottom of every public bio page
- `/compare/bitly-alternative` - "Free Bitly alternative without tracking": a static comparison page (`WebPage` + breadcrumbs, no ratings) with a short answer, a side-by-side table of hrva.cc and Bitly's Free plan (a real `<table>` that stacks into labelled rows below `sm`, with explicit `role`s on every table element because `display: block` drops the native table semantics), when Bitly is the better choice, more about hrva.cc, moving links over and a call to action. Every Bitly cell links its source, and the page says when the facts were checked. `lib/comparisons.ts` holds `BITLY_COMPARISON` (`path`, `published`, `checkedOn`, the two Bitly source URLs). **While `published` is `false` the page is `noindex, nofollow`, stays out of the sitemap and gets no footer link; the owner signs off the table, then flips it to `true`.** Re-check the Bitly facts (and update `checkedOn`) every quarter and whenever the table changes

- `/unsubscribe?token=` - the one-click unsubscribe page (`app/unsubscribe/`): `layout.tsx` sets `title: "Unsubscribe"`, `robots` noindex and nofollow, and `referrer: "no-referrer"`. Before the click it asks `Stop getting {EMAIL_NOTIFICATION_NOUNS[type]} from hrva.cc?`, the type read from the token's unsigned first part by `unsubscribeTokenType` (`lib/notifications.ts`; any other token reads `Stop getting this kind of email from hrva.cc?`, and only the backend decides). **Unsubscribe** POSTs `notificationApi.unsubscribe(token)`; nothing is revoked on load (the backend's GET only redirects here, so link scanners revoke nothing). After it: `Done. You won't get {EMAIL_NOTIFICATION_NOUNS[type]} any more.` or `{Noun} were already off.` (`Weekly summary emails were already off.`), then a link to `/dashboard/settings#notifications`, and `history.replaceState` drops the token from the address bar and history. The result is also kept in `sessionStorage` (`hrva:unsubscribed`, the type and `alreadyOff` only, every access in try/catch), so a reload of the token-less `/unsubscribe` in that tab shows the done line again instead of the invalid link. No token or a 400 shows the backend's invalid-link text in `role="alert"`, a 429 its text; focus moves to the result heading (`tabIndex={-1}`). `SiteHeader` and `SiteFooter` sit outside the `Suspense` boundary
- `/stats` — "hrva.cc in numbers", the public site-wide numbers: a static server page (`SiteHeader`, `SiteFooter`, no data fetching) around the client `PublicStats` (`components/public-stats.tsx`), which loads `GET /public/stats` in the browser through `usePublicStats()`. The lead says most numbers cover the last 30 full days. In order: the date line (`from` – `to`, then "Updated" as a relative time), Active links, Links created and Clicks, a 30-day `ClicksChart` without the visitors line ("No clicks in the last 30 days." over it when the 30-day clicks are 0), Keeping links safe (Harmful links blocked: the last 30 days, with the all-time count in its hint; Visitor reports handled; Average review time as `formatDuration` ("1 h 36 min", spoken "1 hour 36 minutes" in an sr-only span) or "No reviews in the last 30 days"), Blocklists in use (name wrapped, Blocks links / Flags links for a person to check, domains; empty: "No blocklists are loaded right now."), and links to the phishing blog post, `/help/stats#numbers` and `/privacy`. Nothing on it is about a single link or person. The error state reads "Couldn't load the numbers." (`role="alert"`). A 429 adds the backend's text and has no Try again button, like `AnalyticsError` with a refusal. Otherwise Try again calls `refetch()`: the box and the focus stay on the button while it runs (`aria-disabled`, an sr-only status "Trying again"). Focus never drops to `body` when the box changes: if the visitor started the retry, or the box held focus when it changed (an automatic refetch on window focus included), focus moves to the date line once the numbers arrive, or to the alert text (`tabIndex={-1}`) when Try again disappears because of a 429. The box and the button report losing focus from a layout-effect cleanup, which runs before React removes their DOM, and focus moves only while `document.activeElement` is `body`, so it is never taken from somewhere else. Once numbers are loaded, a failed background refetch keeps them. The backend answers with `Cache-Control: public, max-age=600`, so a browser that loaded the numbers in the last 10 minutes doesn't ask again (use a fresh profile when checking locally). The footer's **Product** column links to it as **Public stats**, after Check a link (the page keeps its own title), and it is in `app/sitemap.ts`
- `/unavailable?s=&reason=` - Where the backend sends a short link that can't redirect (`noindex`). `reason` is `blocked`, `expired`, `limit`, `inactive`, `missing` or `domain` (a link on a turned-off custom domain: `This link's domain is turned off right now.`); anything else falls back to the `missing` line. "Report a link" carries `s` to `/report`
- Custom domain links: the backend sends an unavailable link on a custom host to `/unavailable?s={alias}&reason={reason}&d={hostname}` and a password link to `/protected/{alias}?domain={hostname}`. Both pages show `{hostname}/{alias}` (a value that isn't hostname-shaped, `isHostnameShaped`, is left out of the address shown), and `/protected` sends `domain` with the unlock call
- `/report?s=` — Public report form: short link (prefilled from `s`), category, details. The link is reduced to its bare code (`hrva.cc/abc` → `abc`, host taken from `getShortBaseUrl()`) before `reportApi.report()`; a 429 shows the backend's text
- `/report` categories: Phishing, Malware, Spam, **Pretends to be someone** (`IMPERSONATION`, for links and bio pages alike) and Something else. The footer links it as **Report abuse**
- `/report` also takes a bio page (`toReportTarget` in `app/report/page.tsx`): `@name`, `hrva.cc/@name` and `app.hrva.cc/bio/name` (any scheme, `www.`, query or fragment) send `shortUrl: "@name"`; a short code is 1–32 characters of `[a-zA-Z0-9_-]`, as in the backend. A prefilled bio page (`?s=%40name`, from **Report this page**) reads **Report a bio page** and asks which link on the page is wrong. An unreadable target, or the backend's 400 starting with `Enter a hrva.cc`, shows `Enter a hrva.cc short link or bio page, like hrva.cc/abc or hrva.cc/@name.` under the field (`flushSync`, then focus). Send is `aria-disabled` + `aria-busy` while sending, never `disabled`, so focus stays on it, and a `submitting` ref ignores a second Enter
- `/bio/[handle]` — Public bio page, see Bio pages below
- `/dashboard/*` — Protected; user's URLs, API keys, settings
  - `/dashboard` — My URLs. The search waits 300 ms after typing stops (`useListSearch`) and is kept in the address as `?search=`. `New URL` (and the empty state's `Shorten a URL`) open the controlled `CreateUrlDialog`, which has no `DialogTrigger`, so its `onCloseAutoFocus` returns focus to the button that opened it, or to `New URL` once that button is gone
  - `/dashboard/api-keys` — API keys. The table starts with active keys (`useMyApiKeys(true)`, `GET /api-keys?active=true`, newest first; Revoke, and the admin-only Edit limit); inactive ones (`active: false`: expired, revoked or out of calls) come a page at a time (`useMyInactiveApiKeys(page, size)`, `GET /api-keys/inactive`, 10 a page, newest first, with the `Pagination` control under the table while they're shown and there's more than one page; N is the page's `totalElements`) in a separate `tbody` below a disclosure row, **Show N expired or revoked keys** (`aria-expanded`, `aria-controls`, collapsed on load). Each inactive key has **Delete key** (`data-remove-row`), confirmed in one page-level `AlertDialog` ("Delete this API key? It's already turned off, so nothing using it will break. This can't be undone."), and **Delete N inactive keys** above the table, shown only when there are inactive keys, opens its own confirmation (the count is fixed when it opens). An active key always needs Revoke first, so deleting a working key takes two actions; there is no renew. Busy guards are `aria-disabled` plus a `submitting` ref, without `pointer-events-none` (a second click would land behind the button and drop focus to `body`). Errors show as `role="alert"` inside the dialog, which stays open; a 404 or 409 also refetches the list. The delete and revoke mutations return their `invalidateQueries`, so the list has refetched when they resolve. Focus never lands on `body`: after a delete it moves to the next inactive row's Delete, else the previous one's, else the disclosure, else **Generate Key**; after the bulk delete to Generate Key; after a Revoke (the row moves into the inactive section) to the next active key's Revoke, else the previous one's, else the disclosure, else Generate Key; after Cancel back to the trigger, or the same fallback if the row has gone. Revoke is confirmed in its own page-level `AlertDialog` (controlled, like Delete, with the masked key) that stays open until the revoke and the refetch have finished, then moves focus in `onCloseAutoFocus` with `preventDefault`, never in a `requestAnimationFrame` after the mutation (TanStack's `setTimeout(0)` notify batch can land after it, so the old check saw the vanished button and focus fell to `body`); a failed revoke shows `role="alert"` in the dialog, and a 404 refetches
  - `/dashboard/settings` — Profile, password (email accounts only), `NotificationsCard`, `CustomDomainsCard`, `SignInMethodsCard` (`components/sign-in-methods-card.tsx`: read-only, each method from `useMe()`'s `signInMethods` with "Last used {date}", no unlink; it loads late, so it sits below Notifications), `PasskeysCard`, `TwoStepCard`, connected apps, data export and account deletion. Notifications sits right after the account basics, above the security cards: it's the setting people come back to, the dead-link badge links to it, and the cards that load late (passkeys, two-step, connected apps) are below it, so they can't push it away after the `#notifications` jump. Ten cards in one column don't need a jump list

### API Client (`lib/api-client.ts`)
- `request<T>(method, path, body?, headers?)` — fetch wrapper with auth token injection
- Reads `localStorage.getItem("auth-token")` and sends it as-is in the `Authorization` header. The stored value already starts with `Bearer ` (the login response's `token`; the OAuth callback adds the prefix)
- `ApiError` class exposes `.status` and `.message`; `REQUEST_FAILED` is the fallback message when a 4xx body has none. A network failure (`fetch` throws; status `0`) or a 5xx without a JSON message (the dev proxy, a Cloudflare error page) gives `CANT_REACH`, "Can't reach hrva.cc right now. Check your connection and try again."; a 5xx with `{ error }` (the Redis-down 503s) keeps its text
- `request()` reads JSON or plain-text bodies (`POST /auth/register` answers with the bare email); error messages come from `error`, `message`, or the joined field messages of a validation response
- Signing in or out clears the React Query cache; a failed `/users/me` only drops the token on 401/403
- API base URL switches by env:

### Auth (`lib/auth-context.tsx`)
- React Context provider wrapping the tree under `Providers`
- On mount: reads `auth-token` from localStorage, calls `GET /users/me` to hydrate user
- `login()` returns a `LoginResult`: `{ status: "signed-in" }` (token stored, user set) or `{ status: "two-step", pendingToken, methods }`. `completeSignIn(signedIn)` stores the token and user for every other way in (passkey, second step, callback)
- `logout()` removes the token, clears the query cache and the user, and dismisses the `Sign in again` toast (`REAUTH_TOAST_ID`). `logoutTo(destination)` does the same and sends the dashboard and admin layouts (and `ProtectedRoute`) to `destination` instead of the sign-in page with `next` (account deletion → `/login`)
- Signed out on a dashboard or admin page (or inside `ProtectedRoute`) → `router.replace("/login?next=" + encodeURIComponent(pathname + search))`, so signing in returns to the same page, query included (a link to `/admin/urls?search=<domain>` opens with the search filled in), and Back doesn't loop. A signed-in non-admin on an admin page is still pushed to `/dashboard`
- `useReauthToast()`: a 401 for a Google or GitHub account shows one persistent `Sign in again` toast (id `REAUTH_TOAST_ID`) with the backend's text (passkey add and remove, account deletion); its action is `logout()`
- `isAdmin` derived from `user.authorities` containing `{ name: "ROLE_ADMIN" }`
- **No route protection middleware** — dashboard/admin layouts redirect client-side via `useEffect`
- `components/protected-route.tsx` (`ProtectedRoute`) has no importer: the dashboard and admin layouts do the same check themselves. It follows the same redirect rule so it stays safe if used again; remove it when convenient

Every save sends `expectedUpdatedAt`, the synced page's `updatedAt` exactly as received; a stale copy gets a 409, and the editor refetches and waits for it (**Checking the latest version…** in the bar, with **Save changes** and **Discard** held), rebases the draft onto the newer page (`rebaseBioDraft`, so both tabs' edits survive) and then shows the message in the bar, or the refetch error if the refetch fails. The first page refetched after a 409 is accepted even when `isOlderBioPage` would ignore it, so a clock skew between writers can't leave the editor answering 409 forever. The backend's older 409, "This page changed. Reload and try again." (a link deleted mid-save), shows as "A link on your page was deleted, so its button was removed. Check your page and save again." (`bioConflictText`), since the refetch has already dropped the button. Every editor response (GET, create, save, handle change) replaces `synced`, so its `updatedAt` stays current. Edits typed during a save are rebased onto the saved page (`rebaseSavedBioDraft`), a refetch older than the page on screen is ignored (`isOlderBioPage`), and everything below that guard reads the `synced` page, not the prop. A hidden page shows the admin's reason and can't be deleted here; a revoked handle shows the reason and **Choose handle**
- **Edge cache** (`custom-worker.mjs`, `lib/bio-edge-cache.ts`, checked by `npm run check:bio`): the Worker entry wraps OpenNext's `.open-next/worker.js` and keeps `/bio/{handle}` and `/bio/{handle}/opengraph-image` in the Workers Cache API (`caches.default`) for 300 s, so a cold render (100-300 ms of CPU on the free plan's 10 ms budget) runs about once per 5 minutes per data centre. No KV, R2 or other new resource: the static-assets incremental cache is read-only, so `revalidate = 300` would need KV or R2. Rules, all in `bioCacheKey` and `isStorableBioResponse`:
  - only `GET`, only a lower-case 3-30 character handle path (a `%40` or upper-case segment gets its 308 uncached), never a request with `RSC`, `Next-Router-Prefetch`, `Next-Router-State-Tree`, `Next-Router-Segment-Prefetch` or `Next-Action` headers or `_rsc` (the router's flight payload lives at the same URL)
  - the page is cached only without a query string (the backend's `/@{handle}` redirect drops the query); the image ignores its query (`?{hash}` from the metadata). The editor's **View page** adds `?saved={updatedAt}` (`freshBioPagePath`), so the owner always sees the saved version, and the admin links to a page (`BioPageLink` in the Bio pages table and the review queue) add `?saved={hiddenAt ?? updatedAt}`, or `?admin` where the entry has neither (`adminBioPagePath`), so admins always see the live state
  - the key is the URL only, `{origin}{path}?v={version id}` (the version changes per deploy, never per request): cookies, `Authorization`, the user agent and every other request header are left out, which is safe because the page and the image read no cookies or headers (sign-in is a token in `localStorage` the server never sees, and the view beacon is a client-side `POST` with `credentials: "omit"`, so views still count on a hit). The version id comes from the `CF_VERSION_METADATA` binding (`version_metadata` in `wrangler.jsonc`), so a deploy never serves HTML that points at the previous build's chunks; without the binding nothing is cached. The path is tested on the raw URL first, so every other request passes through without a header lookup or a `new URL`. Link-preview bots get the copy a browser warmed, which is fine: the page waits for its data before the shell, so `<title>`, `og:*`, `description` and `robots` are in `<head>` in the browser render too (checked on a wrangler dev render)
  - only a `200` without `Set-Cookie` is stored: a 404 (unknown, hidden, handle-less or deactivated owner's page), a 308 and a 500 always go to Next. A stored copy gets `Cache-Control: public, max-age=0, s-maxage=300` and `Vary: Accept-Encoding`, so browsers revalidate every time and a page hidden, deleted or renamed is gone everywhere within 5 minutes; the help page and the change-handle and delete dialogs say "within 5 minutes"
  - every response it handles carries `X-Bio-Cache: HIT` or `MISS`. The Cache API is a no-op on `*.workers.dev`, so check it on `app.hrva.cc`: `curl -sI https://app.hrva.cc/bio/{handle} | grep -i x-bio-cache` twice (MISS, then HIT), and MISS again after 5 minutes; and `curl -sI https://app.hrva.cc/bio/{missing-or-hidden-handle}` answers 404 with no `X-Bio-Cache` header
- **Retry focus**: every bio screen's Retry (editor, bio analytics, admin bio pages, the review section, the picker) goes through `useFocusAfterRetry(target, ready)`: the click sets a flag, a failed refetch clears it, and once `ready` turns true the target (the screen's heading) takes focus if the vanished Retry left it on `body`. ## Gotchas
- **`UtmFields` reads recent values only after hydration**: the datalist suggestions come from `localStorage` through `useSyncExternalStore` with a `null` server snapshot (and a cached client snapshot), never during render. `/utm` starts with the section open, so reading storage in render made the server and client HTML differ

- **No `.env` files** — API base URL is hardcoded in `lib/utils.ts` and switches on `NODE_ENV`
- **Pointing dev at another backend**: set `DEV_API_ORIGIN` (default `http://localhost:8080`; see Commands), e.g. `DEV_API_ORIGIN=http://localhost:18082 npm run dev -- -p 3002`; it feeds the four rewrites in `next.config.mjs` and `getShortBaseUrl()` in `lib/utils.ts` (inlined through `env`), so never edit those to change ports. The backend's `app.frontend-url` decides where `/unavailable` and OAuth redirects go (3000 by default), so point it at the dev server's port
- **Auth token is stored with its `Bearer ` prefix** — `request()` adds nothing, so a token injected into `auth-token` by hand must include it
- **No middleware-based route protection** — dashboard/admin check auth in a client `useEffect`, creating a flash of unauthenticated content
- **`@/*` maps to root** — unlike the common Next.js pattern of mapping to `src/*`
- **Backend date-times are UTC with no offset** in production, where the container runs in UTC (`LocalDateTime`, e.g. `2026-10-24T09:15:00`); a backend run locally with `mvn spring-boot:run` sends the host's zone instead, so parsed times there show ahead by the host's offset (start the JVM with `-Duser.timezone=UTC` to match production). `new Date()` reads a string without an offset as local time, so it's off by the viewer's offset. Every admin screen parses them with `parseServerDateTime()` (`lib/analytics.ts`) before `formatDateTime()` / `formatTimeAgo()`, as do the analytics views and the dashboard's Created column; parse a nullable field behind a check (`value ? formatDateTime(parseServerDateTime(value)) : "—"`)
- **pnpm/npm**: lockfile is `package-lock.json` (npm), not pnpm
- **Changelog page** at `/changelog` is a client component — fetches changelog JSON from backend `/api/changelog`
- **Easter eggs**: Konami code (↑↑↓↓←→←→BA) on landing page, `/fortune`, `/egg`, console message hint
- **Animations**: `animate-copy-pulse` class, `CountUp` component for stat counters, staggered row entrance via `animate-fade-in` with inline delay, filter remount via `filterKey` 
- **Passkeys locally**: open the FE at `http://localhost:<port>`, never `127.0.0.1`, or the RP ID `localhost` (backend `application-local.yaml`) won't match. The backend's `app.passkeys.allowed-origins` must list that exact origin, e.g. `APP_PASSKEYS_ALLOWED_ORIGINS=http://localhost:3001` for a dev server on 3001
- **One WebAuthn request at a time**: a pending conditional (autofill) request must be aborted before another `navigator.credentials.get()` or `create()`. `getPasskey` and `createPasskey` abort the previous one; components abort their own on unmount
- **Help pages quote UI labels**: `/help/passkeys` names buttons, card titles, badges, their explanations and the email subject exactly (`Add a passkey or security key`, `Turn on with my passkeys`, `Use a passkey or security key`, `Copy codes`, `Download (.txt)`, `I've saved them`, `Use a different account`, `Lost your passkey or codes?`, `Sign-in methods`, …). `/help/stats` quotes the `/stats` labels (Active links, Links created, Clicks, Harmful links blocked, Visitor reports handled, Average review time, No reviews in the last 30 days, Blocklists in use, Blocks links, Flags links for a person to check) and the QR ones (URLs, Show QR code and View stats as the icons' screen-reader names, PNG, SVG, QR scans and other clicks). Change the page with the label
- **Every hrva.cc QR code carries the marker**: the three QR makers (`QrCustomizer`'s PNG canvas and SVG export, the signed-in home form's result, the create dialog) encode `withQrMarker(shortLink)`, so a scan opens `.../<alias>?qr` and counts as a QR scan; the backend drops `?qr` before redirecting. The shown link, its `href` and every copy button stay the plain short link. `QrCustomizer` (the dashboard's QR Code dialog) says under the code "Scans of this code show as QR scans in the link's stats." (no date; the app copy never dates QR scans). The landing illustration (`https://hrva.cc`), the egg and the TOTP codes aren't short links and stay unmarked. A new QR code of a short link must use `withQrMarker`. The one exception is `/qr`, whose codes hold any address the visitor types, so it passes `marker={false}` to `QrCustomizer` (which then also hides its scans caption) until the visitor switches to a short link
- **Header and footer outside `Suspense`**: a page that reads `useSearchParams()` (`/report`, `/unavailable`) keeps `SiteHeader`, `SiteFooter` and everything that doesn't depend on the query outside its `Suspense` boundary, and the fallback is only the query-dependent part. A dynamic render streams the fallback and the resolved content into the same HTML, so a fallback holding the whole page sent two headers and two footers
- **Dev server over a production build**: `next dev` started on a `.next` left by `npm run build` reloads every page in a loop ("Compiled in 1ms"). Move `.next` aside first (`mv .next <somewhere>/next-prod-old`, never delete it), and run `npm run build` only after the dev server has stopped
- **Landing privacy figure** — The landing page's privacy figure quotes `UniqueVisitorCounter.visitorHash` and `AnalyticsDays.SALT_GRACE` by line number on GitHub; update the lines and the `#L` anchors when those files change
- **Bio pages quote labels too**: `/help/link-in-bio` names the editor's labels, badges and messages exactly (`Create page`, `Add from my links`, `Search your links`, `Drag, or use the arrow keys`, `Show on page`, `Save changes`, `You have unsaved changes`, the five link-state badges, `Change handle`, `Choose handle`, `Allow search engines to index this page`, `Report this page`, `Delete bio page`, …). Change the page with the label
- **Notifications help quotes labels too**: `/help/notifications` names the Settings card's labels and messages exactly (`Notifications`, `How notifications work`, `Email`, `Dead links`, `Weekly summary`, `Expiry reminders`, `On since`, `Chat apps and webhooks`, `Add channel`, `Type`, `Name`, the five `CHANNEL_TYPES` labels, `Webhook URL`, `Bot token`, `Chat ID`, `Topic URL`, `Access token (optional)`, `URL`, `How to get this`, `This looks like a Discord URL.`, `Switch to Discord`, `Send me` and the four `CHANNEL_EVENT_LABELS`, `Send test`, `Sent. Check Discord.`, `No deliveries yet.`, `Last delivered`, `Last delivery failed`, `On`, `Off`, `Edit`, `Saved. Leave empty to keep it.`, `Delete`, `Your signing secret`, `Copy secret`, `I've saved it`, `New signing secret`, the auto-off `deliveryLine`, `Destination looks dead`, `The page wasn't found (404).`, `Unsubscribe`, `Done. You won't get weekly summary emails any more.`, `Weekly summary emails were already off.`), and the event hints in its own words. Change the page with the label
- **Every short link uses its own domain**: a link's `domain` (`DomainRef`, absent for hrva.cc) decides its host. Build addresses with `formatShortUrl(short, hostname?)` and hosts with `shortHostOf(hostname?)` (`lib/utils.ts`); never build `hrva.cc/{alias}` by hand
- **The review badge counts three queues**: `useReviewCount` adds the link review queue, the bio page reviews and the pending domain applications (`Promise.allSettled`, so one failing call doesn't hide the others)
- **Custom domains help quotes labels too**: `/help/custom-domains` names the card's labels and messages exactly (`Custom domains`, `How custom domains work`, `Apply for a domain`, `Domain`, `What will you use it for?`, `Apply`, `Application sent. We'll email you when it's reviewed.`, `Withdraw application`, `Note from the admin`, `Copy`, `How to add a CNAME`, `Last checked`, `Check now`, `Retry`, `Remove`, `What happens to its links?`, `Remove domain`, `Removed go.example.com.`, `Custom domains aren't available right now.`, the backend's `problemText`s, the two `disabledNote` texts and the emoji refusal), and renders `DOMAIN_STATUS_LABELS`, `DOMAIN_STATUS_HINTS` (except `AWAITING_DNS`, reworded in `HELP_STATUS_HINTS`), `DOMAIN_STEP_LABELS`, `LINK_MODE_LABELS`, `LINK_MODE_HINTS`, `DOMAIN_PROBLEM_FOLLOW_UPS`, `PROVISIONING_FAILED_TEXT`, `PROVISIONING_GAVE_UP_TEXT` and `domainLimitLine` from `lib/domains.ts`. Change the page with the label
- **Masks aren't truncation**: channel addresses arrive from the backend already masked (`maskedTarget`: scheme and host, four bullets, then the last 4 characters; `Bot` and four bullets for Telegram). Show them whole and wrapped (`[overflow-wrap:anywhere]`); never shorten them further, add a tooltip or rebuild them in the FE
- **`/unsubscribe` keeps the header and footer outside `Suspense`**, like `/report`: only the card is the fallback, so the page never renders without its header
- **Share image fonts**: the OG route may only draw `ogSafeText` output, because `@vercel/og` fetches Google Fonts and emoji for any glyph its bundled Geist lacks. After a Next upgrade, re-run `fc-query` on `node_modules/next/dist/compiled/@vercel/og/Geist-Regular.ttf` and compare it with the ranges in `lib/bio.ts`

- **Install help quotes labels too**: `/help/install-app` names `Shorten a shared link`, `Shared link`, `Shorten`, `No link found in what was shared.`, the form's `Custom alias`, `Visit limit`, `Expires` and `Campaign tracking (UTM)`, the shortcuts `New link` and `My links`, `My URLs`, the offline page's text and `Try again`. Change the page with the label
- **Invisible characters**: `npm run check:bio` starts with `check:invisible`, which fails on zero-width, bidi and other invisible characters in `lib`, `app`, `components` and `scripts`. Build such characters from code points (`String.fromCodePoint`), never paste them
